# The app against section 14, 4 October 2026

Backlog items PERF-1 and RSC-1. Search speed, writing speed and index size at the reference size were measured on 3 October ([2026-10-03-phase0.md](2026-10-03-phase0.md)); this adds the app's start-up and memory, scanning, and embedding in each resource mode.

## Conditions

- **Machine:** the owner's laptop, Intel i7-13620H (16 logical processors), 16 GB of RAM, Windows 11, SSD. It is faster than the spec's reference laptop (four cores, about 2020, 8 GB): every figure below must be measured again on such a machine before release.
- **Build:** release, with the files laid out as the packages install them.

### How each was measured

- **Start-up and idle memory:** `scripts/measure-app.ps1`, three runs. The app logs when its window first asks for the status (`interface.ready`) and when the model is ready (`model.ready`), in milliseconds since the program started. Memory is the private memory of the app and its WebView2 processes, 15 seconds after start, with indexing paused: 162 MB for Catchword itself, with the model loaded, and 150 MB for six WebView2 processes. Their working set adds up to about 505 MB, but it counts pages shared between processes more than once.
- **Scanning:** `cargo test --release -p catchword-service --test measure -- --ignored --nocapture`: 100 folders of 100 notes of about 150 words, words only.
- **Embedding:** `cargo test --release -p catchword-desktop measure_embedding -- --ignored --nocapture`: 120 passages of 300 words, one at a time, as indexing embeds them.

| Mode | Threads | Passages a second |
| --- | ---: | ---: |
| Light | 1 | 5.6 |
| Balanced (default) | 8 | 16.7 |
| Fast | 15 | 17.9 |

- **Indexing peak:** the command-line tool, run from the packaged files, indexing and embedding 300 notes of 700 words: at most 357 MB private, in 60 s. The app's peak is that plus its web view's 150 MB.

## What this means

- **Meaning search arrives 1.7 s after start.** Searches by words work from the first moment; meaning joins when the model is ready. Much of the wait is checking the model's checksums on every start (123 MB of SHA-256) and reading its 25 MB tokenizer. Remembering a good check by file size and date would save most of the first part. *Corrected on 25 November 2026: the checksums take about 0.1 s, not most of the wait. See the update below.*
- **Embedding misses 20 a second even here,** as the Phase 0 benchmark found (ADR-20). Fast is barely quicker than Balanced: past eight threads, more cores do not help.
- **Batching does not help.** Section 14 names batching passages of similar length as the next step, so it was measured in the same test, in the default mode, with 1, 2, 4, 8 and 16 passages per call: 7.0, 7.1, 6.8, 6.6 and 7.2 passages a second. On this processor the model is limited by computation, not by the cost of each call, so batching was not built. (That run had other programs using half the processor, a video encoder among them; Catchword, at low priority, got the rest, as intended, which is why it is half the figure above.) What is left is a smaller or faster model, which ADR-20 weighed and decided against for now.
- **The model is never released.** The target speaks of memory "with the model released"; the app keeps it loaded (section 12, caching). At 312 MB with it loaded, the target is met anyway.
- **Update, 5 October 2026: the model is now released after 10 minutes without a search or indexing.** A probe process that loaded the model, used it once, dropped it and loaded it again held 161 MB private with the model loaded and 21 MB after it was dropped: about 140 MB given back. Loading it again took about 2 s, with a short peak near 300 MB. Idle memory with the model released should therefore be about 170 MB with the web view; that is an estimate from the probe, not yet measured in the app.

## Update, 25 November 2026: meaning search ready within 1.5 s

Same laptop, ONNX Runtime 1.31.1, SQLite 3.54.1.

- **Where the wait went.** Each step of loading the model timed four times: checking the model's checksum 70 to 130 ms, the tokenizer's 17 to 31 ms, reading the tokenizer 1.0 to 1.4 s, starting ONNX Runtime and the model about 0.6 to 1.0 s. They ran one after the other. So the checksums were never the problem, and remembering a passed check would have saved only about 0.1 s.
- **The change.** The model and its tokenizer now load at the same time, on two threads (`Embedder::load` in `crates/embed/src/lib.rs`). Each file is still checked before anything reads it, every time (ADR-18 unchanged). The load itself went from 2.1 to 2.4 s down to 1.2 to 1.5 s.
- **In the app**, `scripts/measure-app.ps1`, back to back:

| Build | Window ready | Meaning search ready | Private memory |
| --- | --- | --- | --- |
| Before (installed `29ce228`, 3 runs) | 0.62 to 1.05 s | 1.75 to 1.80 s; 2.45 s on the first run | 319 to 373 MB |
| After (`target\try-app`, 5 runs) | 0.54 to 0.99 s | 1.14 to 1.28 s; 1.59 s on the first run | 319 to 324 MB |

  The target (under 1.5 s) is met on warm starts. The first start after a new program is copied in is slower, as Windows reads everything from disk. It must still be measured on the reference laptop.
- **Embedding, for the owner's decision.** Several passages at once, each model on a share of the same eight threads (a temporary test, 120 passages of 300 words, two rounds): one model on 8 threads 14.1 to 14.8 a second; two on 4 each 17.0 to 17.1; four on 2 each 19.0 to 19.3. That is about 30% faster for the same processor share, still just under 20. Each extra model costs about 140 MB while indexing (three extra: about 420 MB, within the 1.5 GB peak). Vectors are unchanged, since each passage is still embedded on its own. The owner approved it the same day, and it was built (ADR-25).
- **Embedding with copies, as built.** `cargo test --release -p catchword-desktop measure_copies -- --ignored --nocapture`: 400 notes of about 250 words, embedded through the service, as the app does. One model on 8 threads gave 15.8 passages a second. Four copies on 2 threads each gave 20.3, including the time to make them. The target (20) is met on this laptop. The copies share the model's tokenizer and are made one after another. The test process peaked at 744 MB, against 201 MB with one model. A first version, with four full copies loaded at once, peaked at 1,565 MB.
