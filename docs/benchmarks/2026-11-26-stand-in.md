# A stand-in for the reference laptop, 26 November 2026

Section 14 of the specification sets its targets on a reference laptop: four cores and eight logical processors, from about 2020, with 8 GB of memory. No such laptop has been available, and every earlier figure comes from the owner's faster one. This measures the app on a stand-in for it: the owner's laptop restricted to its four efficiency cores.

It is a forecast, not the measurement the release checklist asks for. That must still be made on a real reference laptop.

## Why the efficiency cores

- **The owner's laptop** has an Intel i7-13620H: six performance cores with two threads each (logical processors 0 to 11) and four efficiency cores with one thread each (12 to 15), as Windows reports them (`GetSystemCpuSetInformation`).
- **The efficiency cores are about as fast per clock as Intel's laptop cores of 2015 to 2020** (the Skylake design, which the common four-core laptops of 2020 still used), and run at up to 3.6 GHz. A 2020 four-core laptop on battery-friendly power limits runs its four cores at about 3 GHz. So four efficiency cores should be roughly as fast as the reference laptop's four cores.
- **The differences:**
  - The stand-in has four threads, not eight. The default mode uses only half the logical processors (four threads on the reference laptop), so this matters little.
  - Its memory is faster.
  - A 2020 AMD laptop (Ryzen 4000) would be faster than the stand-in.
  - Treat the figures as accurate to about a third either way.
- **How:** each program ran with its processor affinity set to processors 12 to 15 (mask `F000`), which the processes it starts inherit. The PC was plugged in, on the Balanced power plan, and about 10% busy with other programs.

## How each was measured

- **Search:** `catchword-eval scale`: 250,000 synthetic passages, 50 queries, as in [the Phase 0 benchmark](2026-10-03-phase0.md).
  - Stand-in: words 98 ms median and 166 ms at the 95th percentile; meaning 593 and 619 ms; combined 715 and 777 ms.
  - Writing the passages and the keyword index took 90 s; the vectors, 16 s.
- **Embedding:** `measure_copies` (in `apps/desktop/src-tauri/src/indexing.rs`), 400 notes of about 250 words through the service, model loading and copying included.
  - It now measures the default mode twice: as this PC splits it (16 logical processors: one model on 8 threads, or four copies on 2 threads each), then as the reference laptop would (8: one model on 4 threads, or two copies on 2 each).
  - Rust's count of logical processors ignores the affinity: the program saw 16 even when held to 4. So the second split is the one that stands for the reference laptop: 6.0 a second with one model, 7.0 with two copies. The first split, crowded onto four cores, gave 5.9 and 6.4.
- **Scanning:** the measurement test in `crates/service/tests/measure.rs`: 10,000 notes, words only.
- **Start-up and memory:** `scripts/measure-app.ps1 -Affinity F000`, the installed app (`dcc60f3`), two sets of three runs. The script sets the affinity as soon as the app starts. The WebView2 processes it starts later inherit it.

## Two things found on the way

- **The owner's laptop was slower today than on 3 October.** Combined search on the performance cores took 449 to 483 ms at the 95th percentile, against 330 ms then.
  - To tell whether SQLite 3.54.1 (25 November) was the cause, the evaluation tool was built from just before that update (SQLite 3.53.2) and run back to back on the same cores: 483 ms. The code is not slower. The machine is, today: heat, power state or other programs.
  - Run on the whole processor from a background shell, the same measurement gave 616 ms, because Windows put part of it on the efficiency cores. Measure with a fixed affinity.
- **`scripts/measure-app.ps1` could count other programs' memory.**
  - Windows reuses process ids. An older program whose parent had once had the id the app was given was counted as the app's own. One run reported 17 processes and 2,020 MB, while the app was idle and indexing nothing.
  - The script now counts only processes started after the app. Figures measured before were not affected, as far as can be told: each was three runs agreeing with one another.

## What this means

On a laptop like the reference, four targets would probably be missed. Each needs the owner's decision, since the specification says the Phase 0 benchmark "confirms or revises" them and that quantisation comes "only when a measured target is missed".

- **Combined search (777 ms against 500).** Scanning 250,000 vectors exactly takes 600 ms here. The specification's next tier is quantised vectors, then rescoring the best with the full vectors. Fixed the same day without them (below).
- **Keyword search (166 ms against 100).** Fixed the same day (below).
- **Embedding (7 a second against 20).** The reference corpus would take about 10 hours, not 3.5. The specification's own answers are a smaller model (weighed and set aside in ADR-20) or, later, a graphics processor or NPU. Otherwise the target is revised. Search by words works from the first minutes in any case.
- **Meaning ready at start (about 2.2 s against 1.5).** Search by words works at once; meaning joins when the model is ready.

## Later the same day: keyword and combined search fixed

The owner approved quantised vectors for combined search, and a study of keyword search. Measuring both showed where the time went: SQLite reading its file one 4 KB page at a time, with a call to the system for each. ADR-26 has the details and the options weighed.

- **The index in its usual place is now read through a memory map.** Results stay exact. A moved index, which may be on a drive that is unplugged, is read as before.
- **Keyword matches are sorted by FTS5's rank.** It is the same score as before, but snippets and highlights are now worked out only for the passages kept, not for every match. The evaluation set gives the same scores to the last digit.
- **Quantised vectors were measured and left for larger libraries.** 1-bit copies lost too many results. 8-bit copies lost none, but were not needed at this size.

`catchword-eval scale` on the efficiency cores, two runs each, 95th percentiles:

| | Before | Sorted by rank (a moved index) | Mapped and sorted by rank (the usual place) | Target |
| --- | ---: | ---: | ---: | ---: |
| Keyword search | 133 ms | 59 ms | 47 ms | 100 ms |
| Vector search | 493 to 500 ms | 492 ms | 155 to 160 ms | |
| Combined search | 630 to 638 ms | 558 ms | 205 to 210 ms | 500 ms |

"Before" is a little faster here than the morning's 166 and 777 ms. The search now runs on a connection of its own, as in the app, where the morning's shared a connection with the writing. The machine's state may also differ.

On the owner's laptop (performance cores), mapped and sorted by rank: keyword 24 ms, vector 80 ms, combined 107 ms; read without the map, 33, 289 and 323 ms.

So on the stand-in, two targets are left: meaning ready at start, and embedding.
